Environment

  • ANTHROPIC_API_KEY — required. Also needed as a GitHub Actions secret for the monthly refresh, which is not yet set, so that cron does not currently fire.
  • DAILY_LIMIT_USD — the spend ceiling, set to 15 in render.yaml. Unset means no limit, which is right locally and wrong for a shared link.
  • DATABASE_URL — wired automatically from the declared Render database. Absent, sessions and claim codes fall back to memory and disk.
  • ANTHROPIC_MODEL / ANTHROPIC_FAST_MODEL — the planner model and everything else.
  • DATA_DIR — where file-backed claim codes and the event ledger live.

Save / restore code<0.5sDisk, no model
Ask Marisol4–6s—

Two things the median hides. When the inspector rejects a plan, the automatic retry roughly doubles the wait: a live run reproduced 111 seconds. The customer still gets a correct plan and never learns a draft was thrown away, but he waits twice. And the draft ticker does not fill steadily from twenty seconds in, as was once assumed here: measured, the stream held 830 characters at 46 seconds and 7,400 arrived in the last five. Generation is thinking-bound, not writing-bound, so the ticker is honest company rather than an early read of the plan.

The honest bottleneck is Elena's minute — and it's now a minute the customer watches work happen in: his own items appearing line by line, Kyla's tips, real store facts. Fast-mode (already wired with automatic fallback) halves it whenever Anthropic capacity opens.

Data systems

The knowledge the agents stand on

  • Store directory — 50 curated Houston stores with knownFor, catersTo, howToBuy, contact, price tier; closed stores auto-filtered.
  • Houston knowledge packs — events calendar (CERAWeek, OTC, rodeo, gala season), shopping districts with drive times, industry dress-code decoder, face/body playbook, price-and-timing reality tables, Kyla's style gems and life-moments playbook.
  • Self-refreshing layer (Ryan) — monthly web research writes generated files: per-store status + insider notes, a rolling 90-day season brief, a retailer price brief. Seasonal crons add weekly pulses in Nov–Dec and July plus pre-event sweeps. Guards reject stale-dated facts and search-failure apologies.
  • Claim-code memory — Postgres-backed dossiers, falling back to files with no database (profile, plan, purchases, photo read, chat history, outfit matrix) under human-readable codes; guest-first, no passwords.
  • The receipt book — append-only event ledger (interviews, plans with store ids, saves, restores, questions, outfits, and the cost of every individual model call) with an aggregate /api/stats — the countable evidence for store-partnership deals. It reads from whichever store it wrote to; reading the file while writing to the database made every number in production read zero.

Quality machinery

What keeps bad output from shipping

  • The deterministic inspector — every plan checked in code before serving: phase sums vs total, one-time plans vs stated budget (the "$400 became $1,600" class), banned colors in item names, unknown store ids. Failures auto-regenerate.
  • Schema-enforced caps — word limits live in tool schemas, not just prompts; script fields structurally limited to what a man reads standing in a store.
  • Conversational guardrails — never re-ask the answered, never accuse of dodging, budget-ambiguity chip with conservative default, send-off travels with the submit call, "north star" never printed.
  • Resilience — plan retry (2 attempts), streaming fallback to plain requests, photo-failure and session-loss messages that tell the truth, rate limiting on Claude-calling routes only, trust-proxy correct.
  • Two ways the server used to die, both reproduced before they were fixed — a single GET /api/session/<unknown id> killed the whole process, because Express 4 does not forward a rejected promise from an async handler to the error middleware and Node treats the unhandled rejection as fatal. Anyone with the URL could do it with one request. Separately, a dropped idle database connection did the same: pg emits error on the pool and an EventEmitter with no listener throws, and managed Postgres drops idle connections as a matter of routine. Both are fixed, and an unhandledRejection handler means the next handler written without a try/catch is a logged 500 rather than an outage. A synchronous throw still exits, because continuing from one is genuinely unsafe and a clean restart is the cheaper mistake.
  • What the database is actually asked to remember — the plan chat, the outfit matrix and a failed plan's error were all written onto the session and never persisted, so a database bought to survive redeploys still lost them. Verified after the fix by killing the process mid-session: Kyla came back still knowing which shoe question had been asked and which outfits depended on the answer. "generating" is deliberately not persisted, since it is a claim about a promise in one process and would otherwise lock out the retry the customer just tapped.
  • The eval set — npm run eval. Ten fixed profiles, each one a failure this build actually hit, scored by 15 deterministic checks per plan: budget arithmetic, per-period cadence, real store ids, banned colours, the tailoring ceiling, voice, length, and lead times on an urgent event. Nothing is model-graded, because a model grading a model is one more thing to debug. It mirrors the route's single retry, so it measures what a customer gets rather than what the first attempt produced.
  • The house voice, enforced — em-dashes are stripped mechanically; the antithesis shape, punchy fragments, banned openers and a sentence-count overrun are detected in code. A flagged intro or sign-off is rewritten by one fast-model call in about two seconds and re-checked before it is accepted, rather than costing a full regenerate. npm run voice:check guards the detector and scans shipped copy.
  • The tailoring ceiling — measured plans were putting 22% and once 42% of a man's budget into alterations. The business sells clothes, so the planner targets 8-12%, the inspector rejects anything past 20%, and two eval checks hold it there.
  • Envelope salvage — the planner has returned a complete plan under a junk top-level key. Rather than pay a minute to regenerate content already in hand, it is recovered. npm run plan:check covers four malformed shapes seen live.
  • Validation history — five personas end-to-end, a 16/16 full-surface sweep, then the eval set that replaced hand-reading as the quality bar.

Operations

How it runs

  • Topology — Expo web app on Vercel; Node/Express + TypeScript API on Render, plus Render Postgres 18 in the same region; Anthropic API for all agent calls. The two halves currently auto-deploy from different branches, which works only until they drift.
  • Is it actually wired? — /api/health answers it directly, reporting storage, persistent and spendLimitUsd. A "memory" there means claim codes die on the next redeploy, a state otherwise indistinguishable from working.
  • CI — GitHub Actions typechecks server and app on every push/PR to main.
  • Refresh — refresh-data.yml on monthly + seasonal crons (needs ANTHROPIC_API_KEY secret); commits regenerated data, Render redeploys.
  • Cost profile, now measured rather than estimated — a plan costs $0.33 to $0.47 of API, attributed per agent by costs.ts and reported at /api/stats. The earlier $0.60-1.50 was a guess and it was pessimistic. Cached input runs $0.15 per hundred thousand tokens against $1.50 fresh, which is the prompt-caching strategy stated in dollars. Chat turns are pennies; a live end-to-end run on 1 September recorded $0.31 for the plan itself. Hosting is no longer the free tier: Render projects about $51 for September across the always-warm API, the Postgres instance and the workspace subscription, the last being the largest single line.
  • The spend ceiling — DAILY_LIMIT_USD stops the Claude-calling routes for the day and says the shop is booked rather than showing an error. The rate limiter caps how fast one person spends; this caps what everyone can spend, which is the failure a shared link actually causes. Its counter is rebuilt from the event log on boot, so a redeploy no longer hands the day a fresh budget: measured, $0.31 of spend sat in the database while a freshly restarted ledger claimed $0.02.
  • Housekeeping — the session hot cache ages out at 24 hours and the pre-warm map expires after 30 minutes. Both leaked before: the database pruner only ever deleted Postgres rows and returned immediately with no database configured, so nothing pruned memory at all.

Large improvements ahead

The big builds, in order of impact

  1. Real accounts. Postgres is already wired behind the claim-code system; what is missing is identity. Email or passkey login, shareable read-only plan links, returning-customer Kyla by default. The foundation every revenue feature stands on.
  2. Progressive plan render. The ticker proves the stream parses; the next step renders finished phases as cards while Elena writes the rest — first phase readable in ~20 seconds.
  3. Native apps. The Expo codebase already targets iOS/Android; App Store presence needs accounts, push notifications (phase reminders: "Week 3 — shoe week"), and the $99/yr Apple program.
  4. Seasonal re-engagement. With accounts: Kyla emails/pushes at the calendar moments the app already knows — "Gala season's six weeks out; your tux plan is ready."
  5. Store portal. Give partner stores a login to see (aggregate) referral counts and post their own trunk-show dates into the directory — turns the receipt book into a product.
  6. Business items from the playbook doc — LLC, trademark, hosting upgrade. The persona renaming is done: the roster carries no third-party identity.

New markets

The city-pack playbook

Everything city-specific already lives in swappable data, which makes a new market a research project, not an engineering one:

  1. Research the pack — 40+ stores with knownFor/catersTo/howToBuy, the city's events calendar, shopping districts with drive times, industry decoder (Dallas: finance/tech/defense; Austin: tech/startup/music). Ryan's script re-verifies it monthly from day one.
  2. Localize the voices — Kyla's Houston references and the team's backstories stay as they are, since none of them names a place; the climate brief rewrites (Dallas heat is real but the AC-swing culture differs; Austin is business-casual-first).
  3. Ship behind a city selector — one codebase, one brand, ?city=dallas loading the pack; never a separate app per city.
  4. Sequence — Dallas first (closest culture match, same store chains plus strong independents), Austin second, then San Antonio/Fort Worth. Each launch re-runs the Houston GTM: local face, event-timed pushes, independent-store partnerships.
  5. Gate — expand only after Houston shows paying users; a second city doubles research and marketing surface, not revenue, until the model is proven.

The women's application

Same engine, richer catalog

Kyla is, if anything, more natural here — and the pipeline needs no structural change. The workstream:

  1. Store pack — Houston womenswear directory (Tootsies, Elizabeth Anthony, Saks/NM women's floors, Abejas, local boutiques, tailors who do womenswear well) with the same knownFor/catersTo depth.
  2. Knowledge packs — women's fit-and-body playbook (the face/body decoder generalizes), occasion decoder (galas, work codes by industry, weddings-as-guest rules differ meaningfully), price-reality tables (alterations pricing differs, MTM is rarer, designer resale matters more).
  3. Interview adjustments — dress codes and categories expand (dresses, skirts, suiting, occasion wear); sizes work differently (and vary by brand — Kyla should say so); the magic question and care craft carry over unchanged.
  4. Planner adjustments — category taxonomy, outfit matrix gains accessories weight, gala season carries more load.
  5. Product shape — one app, "Who are we dressing today?" at the start; shared brand, shared store relationships, shared claim codes. Realistic effort: a few focused weeks, mostly research and prompt work, no new architecture.

The through-line for every expansion: the engine is done. Growth is data packs and voice — researched once, refreshed monthly by machinery that already exists.
